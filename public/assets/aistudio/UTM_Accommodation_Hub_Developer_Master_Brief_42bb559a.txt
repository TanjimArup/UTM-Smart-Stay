1. PROJECT SUMMARY [DECIDED]
--------------------------------------------------------------------------------
An Agoda / Booking.com style web app where UTM students search, compare, and
book student accommodation across UTM's campuses (Johor Bahru, Kuala Lumpur,
Pagoh) through one map-based interface, with a central admin database behind it.

LATEST DIRECTION (overrides earlier documents):
- The app is NO LONGER an add-on inside UTMSmart or any official university
  system.
- It is an OPEN, STANDALONE WEB APP for UTM students.
- Students sign in with PHONE NUMBER + MATRIC NUMBER.
- Transit / shuttle features were already dropped. Scope is 100% accommodation.

3. PROBLEM STATEMENT (THEORY) [DECIDED]
--------------------------------------------------------------------------------
Students across UTM campuses face a fragmented, opaque housing market. They
cannot easily compare on-campus and off-campus options, see real-time
availability, or see exact pricing in one place. Manual application processes
lack self-serve convenience, causing student frustration and admin overload.

Five core problem statements (from the deck, Step 3):
  1. Fragmented Search     - cannot filter colleges across JB, KL, Pagoh in one place
  2. No Map Discovery      - cannot see college locations/distances on a map
  3. Hidden Pricing & Slots- rates and availability buried in static files/PDFs
  4. Manual Booking Friction- paper forms and offline payments delay confirmation
  5. Scattered Admin Records- no central database for multi-campus inventory

Evidence cited in the deck (student survey; sample size and method are NOT
stated in the deck, so do not quote these as rigorous statistics):
  - 18% knew their waitlist position (82% waited blindly)
  - 12% could track application/repair requests
  - 61% struggled with location (off-campus distance and transit)
  - 89% rated a unified add-on "very useful"
  NOTE: the 89% figure was for a UTMSmart add-on; it should not be assumed to
  transfer to a standalone app.

Process used to reach the idea (deck): Understand Context, Gather Insights,
Identify Opportunities, Generate Ideas (brainstorm, mind map, SCAMPER),
Evaluate & Prioritise (scoring matrix), Define the Idea.

Idea scoring (Impact / Feasibility / Unique = Total):
  A. Multi-campus filter & map view ...... 5 / 4 / 4 = 13
  B. Pricing, booking & payment portal ... 5 / 5 / 3 = 13
  C. Admin master inventory database ..... 4 / 5 / 3 = 12
  D. Roommate personality matching ....... 2 / 4 / 3 = 9   (OUT of scope)
  E. IoT smart door locks ................ 3 / 1 / 4 = 8   (OUT of scope)
Project scope = A + B + C only.

6. AUTHENTICATION DESIGN (PHONE + MATRIC)
--------------------------------------------------------------------------------
Requirement [DECIDED]: sign in with phone number and matric number.

Critical fact: a matric number is an identifier, not a secret and not proof.
Anyone who knows or guesses one could claim it. Phone + matric alone proves
nothing about being a UTM student unless one of the following is added.

[SUGGESTED] Minimum viable flow:
  1. User enters phone number and matric number.
  2. System sends a one-time password (OTP) to the phone (SMS or WhatsApp).
  3. User enters OTP. This proves they control the phone number.
  4. System creates/loads the account and issues a session.
  - Phone number is the login credential (via OTP). Matric number is stored
    as a profile attribute and used for booking eligibility.

Uniqueness rules [SUGGESTED]:
  - One account per phone number.
  - One account per matric number (unique constraint).
  - Handle phone number changes and lost phones with a recovery path.

Verification levels (pick one) [OPEN]:
  Level 0: No verification of student status (OTP only). Simplest; anyone can
           claim any matric number. Acceptable only if bookings are payment-
           backed and admins can cancel suspicious ones.
  Level 1: Also verify a UTM email address via OTP (students have UTM emails).
           Strong, cheap, and likely the best option.
  Level 2: Upload student card photo reviewed by admin. Strong but manual.
  Recommendation: browse freely; require Level 1 (or 2) before a booking can
  be completed.

Matric number validation:
  - Validate format with a regex before storing. Example pattern seen in
    practice: letter + 2-digit year + 2 letters + 4 digits (e.g. A24MJ3028).
    Confirm the real formats across all UTM campuses (JB, KL, Pagoh, MJIIT)
    before hardcoding; do not assume one pattern.
  - Normalise to uppercase and trim whitespace.

Phone number handling:
  - Store in E.164 format (e.g. +60123456789). Many students are international
    (Bangladesh and other countries), so do not restrict to +60 numbers.
  - Use a library (e.g. libphonenumber) for validation.

OTP security [SUGGESTED]:
  - 6 digits, expires in 5 minutes, single use, store only a hash.
  - Rate limit per phone and per IP (SMS pumping/abuse is real and costs money).
  - Lock out after repeated failures.
  - Session: HTTP-only secure cookie or short-lived JWT with refresh token.
  - SMS costs money: budget for it or prefer WhatsApp / email OTP.

7. TECHNICAL ARCHITECTURE
--------------------------------------------------------------------------------
From the proposal [DECIDED, keep as direction]:
  - Frontend: web UI with a map SDK (Google Maps API or Mapbox).
  - Backend + database: relational DB (PostgreSQL or MySQL) with relations
    between Campuses, Properties/Colleges, Room_Types, Bookings.
  - Third-party: payment gateway API (Billplz, or similar) for instant payments.
  - The line "built into the existing UTMSmart framework" is SUPERSEDED.

Recommended concrete stack [SUGGESTED] (team to confirm; choose what the team
already knows):
  Frontend : React (Next.js or Vite) + Tailwind; mobile-first responsive design
  Map      : Mapbox GL JS or Google Maps JS API (or Leaflet + OpenStreetMap
             for zero cost)
  Backend  : Node.js (Express/NestJS) or Next.js API routes; REST (or tRPC)
  Database : PostgreSQL (strongly preferred: transactions, row locking,
             constraints, PostGIS for geo queries)
  ORM      : Prisma or Drizzle
  Auth     : custom OTP flow, or a provider (Firebase Auth phone, Twilio
             Verify, Supabase Auth)
  Storage  : S3-compatible bucket / Cloudinary / Supabase Storage for photos
  Hosting  : Vercel/Render/Railway + managed Postgres (Supabase, Neon)
  Payments : see Sec. 9

Design priorities:
  - Mobile-first: students will mostly use phones.
  - Fast browse experience: browsing pages should be public and cacheable.
  - Booking path must be transactional and race-condition safe (Sec. 10).

8. DATA MODEL
--------------------------------------------------------------------------------
Core entities named in the proposal: Campuses, Properties/Colleges, Room_Types,
Bookings. The rest is [SUGGESTED] and needed to make the system work.

campuses
  id, name (Johor Bahru / Kuala Lumpur / Pagoh), code, latitude, longitude

properties            (a college, hostel, or building)
  id, campus_id (FK), name, short_code (e.g. KTDI), type
  (on_campus_college | off_campus_partner), description, address,
  latitude, longitude, gallery (images), amenities, status (active/archived),
  contact info

room_types
  id, property_id (FK), name, occupancy (single / sharing / number of beds),
  gender_restriction (if applicable), amenities, base_price_semester,
  base_price_month, deposit_amount, total_units, active

rooms (optional, if tracking individual rooms)
  id, room_type_id (FK), room_label, status

availability / inventory
  Either computed (total_units minus active bookings per period) or stored as a
  counter per room_type per term. Define the booking period model first (below).

terms / booking_periods
  id, name (e.g. Semester 1 2026/2027), start_date, end_date

users (students)
  id, phone_e164 (UNIQUE), matric_no (UNIQUE), full_name, email,
  utm_email, utm_email_verified, phone_verified, nationality (optional),
  gender (only if needed for allocation), created_at

admins
  id, email, password_hash, role, campus_scope (nullable = all campuses)

bookings
  id, user_id, room_type_id (or room_id), term_id, status
  (pending_payment | confirmed | cancelled | expired | refunded | waitlisted),
  amount_due, amount_paid, created_at, expires_at (hold timer)

payments
  id, booking_id, gateway, gateway_reference, amount, currency, status,
  paid_at, raw_webhook_payload

waitlist_entries
  id, user_id, room_type_id, term_id, position/created_at, status

amenities (lookup) and property_amenities (join)
audit_log (admin actions on prices, bookings, inventory)

Key constraints:
  - UNIQUE(users.phone_e164), UNIQUE(users.matric_no)
  - Prevent a student holding multiple active bookings for the same term
    (confirm the policy).
  - Money stored as integers in sen (or DECIMAL), never floating point.
  - Index lat/long (or use PostGIS) for map queries.

9. PAYMENTS
--------------------------------------------------------------------------------
Requirement [DECIDED]: pay deposit or full fee online via FPX or credit card.

Because the app is no longer tied to UTM's merchant system:
  - [OPEN] Whose merchant account receives the money? Options: the team, a
    registered business, or the property owners. Most Malaysian gateways
    require a registered business (SSM) for live payments, so this blocks
    going live with real money.
  - For the course project, use the gateway's SANDBOX only. Do not move real
    funds without resolving the legal/merchant question.

Candidate gateways [SUGGESTED]: Billplz (named in proposal), ToyyibPay, Stripe
(cards; FPX availability depends on account), SecurePay, Razer Merchant
Services.

Required implementation behaviours:
  - Create the booking as pending_payment with a hold timer (e.g. 15 min).
  - Redirect to gateway; on return, DO NOT trust the browser redirect.
  - Confirm payment through the gateway's WEBHOOK / callback, verifying its
    signature, then mark the booking confirmed.
  - Make webhook handling IDEMPOTENT (gateways resend callbacks).
  - Expire unpaid holds and release the room automatically (scheduled job).
  - Keep refund and cancellation rules explicit (policy is [OPEN]).
  - Store gateway references; never store card data (PCI scope stays with
    the gateway).

10. AVAILABILITY, DOUBLE-BOOKING AND WAITLIST (THE HARD PART)
--------------------------------------------------------------------------------
Stated goal [DECIDED]: bookings automatically update availability and prevent
double-booking without manual staff intervention.

Implementation guidance [SUGGESTED]:
  - Do availability decrement and booking creation inside ONE database
    transaction with row-level locking (SELECT ... FOR UPDATE) or an atomic
    conditional update (UPDATE ... SET available = available - 1
    WHERE available > 0). Never check-then-write in application code.
  - Use a temporary HOLD while the student pays; release on expiry/failure.
  - Test concurrency: two users booking the last unit at the same instant.
  - "Only 3 rooms left!" must read from the same source of truth as booking.

Waitlist mechanics [OPEN - decide before building]:
  - Does the waitlist apply per room type per term?
  - When a unit frees up, is the next person auto-offered with a time window
    to pay, or does an admin allocate?
  - How is the rank displayed and kept fair (FIFO by timestamp)?

Data freshness problem (new because of the pivot):
  Without a university feed, "real-time availability" is only as accurate as
  the data admins enter. Decide who is responsible for keeping inventory
  current. Show a "last updated" timestamp on listings. Be careful: showing
  "3 rooms left" for a room that is actually full is worse than showing nothing.

Booking-period model [OPEN]: per semester, per month, or both. The proposal
shows both semester and monthly pricing. Decide how a monthly booking vs a
semester booking affects inventory.

12. SECURITY, PRIVACY AND LEGAL
--------------------------------------------------------------------------------
Personal data collected: phone, matric number, name, email, booking and
payment records (and possibly gender/nationality).

- Malaysia's PDPA 2010 applies to commercial transactions involving personal
  data. Provide a privacy notice, collect only what is needed, get consent,
  and give a way to delete the account. Confirm applicability with the
  lecturer for a coursework project, but design as if it applies.
- Do not expose one student's data to another: authorise every booking/payment
  endpoint by owner (object-level checks).
- HTTPS everywhere; hash secrets; never commit API keys; use environment
  variables.
- Validate and sanitise all inputs; protect against SQL injection, XSS, CSRF.
- Rate limit login/OTP, booking, and search endpoints.
- Admin actions that change prices, bookings, or inventory must be audit
  logged.
- Image upload: restrict type and size; scan or re-encode.
- Be explicit in the UI that this is an independent student-built platform,
  not an official UTM service. Using UTM names and college names/logos may
  need permission; confirm before public launch.

14. NON-FUNCTIONAL REQUIREMENTS [SUGGESTED]
--------------------------------------------------------------------------------
- Responsive, mobile-first; works on low-end phones and slow connections.
- Accessible: sufficient colour contrast, keyboard navigation, alt text.
- Performance: listing/search pages load in about 2-3 seconds on mobile.
- Reliability: booking and payment flows must be recoverable (no lost money,
  no lost bookings).
- Observability: error logging, payment/webhook logs, basic monitoring.
- Data backups for the database.
- Internationalisation: English first; consider Malay. Support international
  phone numbers and names.
- UI direction from the deck: maroon / dark red primary colour (deck uses a
  deep burgundy with pink accent), clean card-based layout. This is
  presentation styling, not a requirement.
- The team studies HCI (SCSM2113 / HCI usability evaluation in this course
  context), so apply Nielsen's usability heuristics: visibility of system
  status (booking/waitlist status), error prevention (double booking, wrong
  payment), recognition over recall, consistency.
